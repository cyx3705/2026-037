## 它在这一串里站哪一格

```
QQ    ──NapCat──▶ qq-bridge        ─┐
                                     ├─ 统一 HTTP API ──▶ HistoryFama（本模块）──▶ Aurora 页面
钉钉  ──本地库──▶ dingtalk-bridge  ─┘
```

桥负责对接平台、落地、去重、实时推送、发送；**本模块只是消费方**。这条边界是有意的：
新增一个平台 = 新增一个桥 + 用 `fama.bridge.add` 加一条配置，本模块一行代码都不用改。

## 工程约定

- **改动只进 dev 工作区。** 先 `vulcan.dev.start`，在 F 盘工作区里改，`submit` 送审热装，批准后 `finish`。直接改主树最后没法 finish。
- **只用统一契约（宿主 6.0.0 起编译期强制）。** 宿主给的只有一条总线和一个上下文。数据目录走 `context.Environment.DataDirectory`，不拼 `%AppData%`、不用 `Assembly.Location`。✔
- **版本三处一致**：`HistoryFamaVersion.props`、`module.manifest.json`、`project.manifest.json`。不一致时宿主静默跳过整个模块。✔
- **`ModuleInfo.ModuleName` 显式写死 `HistoryFama`**：缺省值是程序集名，同时也是指令域。✔
- **页面 owner = `History` + 首字母大写的指令域 = `HistoryFama`**，与模块名无关；对不上整页被 Aurora 静默拒收。✔
- **界面协议指令**（`fama.ui.describe / actions / data`）只读并带 `HiddenReason`。✔
- **宿主程序集 `Private=false`**：部署时由宿主提供；测试工程反过来 `Private=true`。✔
- **`.ps1` 必须带 UTF-8 BOM**；`SHA256SUMS` 与 manifest 不能带 BOM。✔
- **不定义 `[ComImport]`**（可卸载装载上下文不支持 COM 互操作）。✔
- **不跨仓 ProjectReference**，文档里也不写指向别的仓的相对链接。✔

## 本模块特有的取舍

### 桥配置就是一份 JSON，没有第二种真源

`bridges.json` 在 `context.Environment.DataDirectory`（`%AppData%\HistoryVulcan\ModuleData\HistoryFama\`），
结构 `{"schemaVersion":1,"bridges":[{id,platform,title,baseUrl,token}]}`。
`fama.bridge.add / remove` 是唯一的写入口，内容归模块、**路径归宿主**：

- `token` 传空串是**「别动它」**，不是「清空它」——不会因为漏填一次就把已有凭据抹掉。
- `id` 大小写不敏感地命中同一条，重复 add 是更新而不是新增。
- 配置文件 JSON 坏了就**抛出并说明路径**，不静默当成「没有桥」——否则界面会变成空白且毫无线索。
- 缺 `id` 或缺 `baseUrl` 的条目在读入时跳过，不让半条配置去连网络。

桥的地址与 token 来自 `2026-036-MessageHub/b-Deploy`：`Start.ps1` 跑完会把两条 `base_url + token` 打出来，
`b-Deploy/.env` 里的 `QQ_BRIDGE_TOKEN` / `DINGTALK_BRIDGE_TOKEN` 就是同一个值。

### 模块不留消息缓存

消息的真值在桥的 SQLite 里。本模块**不缓存、不落库、不做增量同步**，每次取数都现问桥。
理由：缓存会立刻带来「本地历史与桥对不上」的一致性问题，而桥本来就快（同机 SQLite）。
代价是桥掉线时界面上是空的——这是刻意的：**宁可显示「离线 + 原因」，也不显示上次的旧数据装作还活着。**
桥表里 `离线` 那行的「能力」列写的就是具体原因（连不上 / 401 / 不是 JSON）。

### 能力为 false 不是错误

`/api/v1/meta` 的 `capabilities` 是桥自己声明的。钉钉桥当前 `send = false`，于是
`fama.msg.send bridge=dingtalk …` 会回一句「钉钉 这条链路还不支持发送（桥把 send 能力标成 false）」，
**不是**异常堆栈。客户端把契约的 `error.code == "unsupported"` 专门翻成人话，其它错误码原样带出桥的消息。

### 发送要人点头

`fama.msg.send` 是 `Level = Ask` 并写了 `ConfirmPrompt`。它是本模块唯一对外部世界产生副作用的指令，
所以也不投影到 MCP（`mcpExposure=readonly` 只放只读的出去）。

### 页面接线由测试钉住

会话表声明通道 `fama.conversation`，消息表按 `{selection.fama.conversation.platform}` /
`{selection.fama.conversation.conversation}` 取数，发送动作按同样的占位符取目标。
这三处任何一处改名都会让界面「点了会话但消息表不动」，而 Aurora 只会静默不取数——
所以离线测试逐条断言了它们，别手改这些常量。

刷新按钮走 `aurora.ui.refreshdata page=fama`。**没有 Aurora 时那是个断链动作**（按钮画成说明原因的牌子），
这是可接受的：本模块 `ui=true`，页面本来就由 Aurora 渲染；指令面不依赖它，控制台照常能用。

## 已知缺口

- **只能发文字。** 桥的发送端点支持 `attachments`（base64），本模块 v1 没接：页面上没有选文件的控件，
  `fama.msg.send` 也没有文件参数。要补就加 Aurora 的 `panel.file` 组件 + 一条把本机文件读成 base64 的参数。
- **不实时。** 桥有 `/api/v1/events`（SSE，契约 4.8），本模块目前靠手点「刷新」，没有订阅。
  要做就得常驻一条 SSE 连接并驱动 `aurora.ui.refreshdata`——注意模块会被热重载，连接要能随卸载收干净。
- **没有翻页。** 两张表都取固定上限（`FamaPage.PageLimit = 200`），只有「最近的」。
  桥的分页游标（`before` / `after` / `has_more`）已经具备，缺的是界面上的「加载更多」。
- **聚合是「各桥取回后再合并排序」**：每桥各取 `limit` 条再合并截断，
  所以某个桥独占前 200 条时其它桥的会话会被挤掉。桥多于两个、或单桥会话数远超 200 时要改成按时间归并。
- **`fama.bridge.list` 会同步探活每个桥**，桥多或桥慢时这条指令就慢（客户端 15 秒超时/次）。
- **没做过真机联调**：本仓的验证是「假桥（TcpListener 照契约回 JSON）+ 宿主 `--probe` 装载」；
  真 QQ / 真钉钉那条链路在 `2026-036-MessageHub` 侧各自有自测，但两端从没在同一个进程里对过。
  第一次真跑时先看 `fama.bridge.test`，再看三张表的联动。
